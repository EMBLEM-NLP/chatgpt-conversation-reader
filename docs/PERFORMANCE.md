# GCR performance baseline

Generated by `npm run perf -- --write-doc --date <date>` (`scripts/perf-baseline.mjs`). **Do not edit the numbers by hand**: re-run the script. The structure of this page is a fixed template in that script.

> **Read this caveat first.** These numbers come from ONE run in ONE shared sandbox with other processes running at the same time, on SYNTHETIC text generated by a seeded PRNG. They are not from a real ChatGPT export, not from a dedicated benchmark machine, and not repeated runs: expect a different machine, a quieter machine or a real export (longer messages, attachments, more branches, much longer words) to give different results. They document the order of magnitude and catch regressions; they are not a guarantee. Speed never fails the build: only correctness does.

## Method

* **Data.** `scripts/perf-baseline.mjs` generates 50,000 messages in 500 conversations (100 messages each) in 5 shards (`conversations-00N.json`) with a seeded PRNG (seed 20261011; no `Math.random`, no clock): the same seed and size always give byte-identical data (SHA-256 `facc7edc01e230f1...`) and the same stored counts. Text is pseudo-words with a Zipf-like frequency plus real topic words (for stemming and prefixes), accented words, CJK sentences, URLs, code blocks and emoji; user messages are about 6-70 words, assistant messages 30-220. About every 20th assistant reply is an abandoned regeneration, so the trees branch (3,500 abandoned leaves in total) and the length of every active thread is known exactly. Raw message text: 30.4 MiB; export JSON 55.9 MiB; ZIP (DEFLATE, in memory) 13.8 MiB.
* **Import, re-import, graph build** run the built CLI (`dist/cli/main.js`) as a child process. Wall time includes about 0.1 s of process start. Peak RSS is the `VmHWM` line of `/proc/self/status` (the high-water mark of the process after it started; on a platform without it `process.resourceUsage().maxRSS`, which on Linux would also count the parent's resident size at fork time and so overstate a child started by this large parent), written by a tiny `--require` hook when the child exits. The children run with `scripts/no-network-guard.cjs` preloaded and the run fails if the guard recorded any network attempt.
* **Searches, get, thread, stats, audit** run through the SDK (`dist/sdk/gcr.js`, read-only handle) in one measurement worker process, each timed with `performance.now()` after five untimed warm-up queries. 200 queries: 80 words from the whole frequency range (rare to ubiquitous), 40 prefixes (`abc*`), 30 phrases (raw FTS5 `"w1 w2"`), 25 CJK substrings of 1-4 characters, 25 hostile strings (operators, quotes, SQL, NUL, a 5,000-character token, control characters). Page size 20. `get` and `thread` are timed for the same 100 pseudo-random conversations, and the length of each returned active thread is checked against the generator's.
* **Correctness gates** (the only way the script fails): stored conversation and message counts (import, idempotent re-import, direct row counts), active-thread lengths, stats totals for every group-by, audit counts, queries that must hit, and an empty guard log.

### Memory against export size

| Messages | Peak RSS of `gcr import` (MiB) | Messages per second |
| --- | --- | --- |
| 10,000 | 122.3 | 6,136 |
| 50,000 | 142.2 | 7,524 |
| 250,000 | 140.3 | 5,929 |

From the middle row to the last the data grew 5x and the peak RSS 0.99x (the run warns above 1.6x). From the first to the middle row they grew 5x and 1.16x. The importer streams the archive and parses one conversation at a time (docs/ARCHITECTURE.md section 5); what it keeps for the whole run is a small record per conversation (its id and a few fields), so memory is bounded by the number of conversations plus the largest single conversation plus SQLite's cache, not by the size of the export (NFR-05). Over this range the peak did not grow with the data (the differences are within what garbage-collection timing explains). These runs are the evidence, for these sizes only, on synthetic conversations of 100 messages; a conversation far larger than that raises the bound.

## Budgets (the NFR-05 baseline targets) and why these numbers

| Budget | Target | Measured | Verdict |
| --- | --- | --- | --- |
| Import throughput | >= 10,000 messages/s | 7,524 messages/s | NOT met |
| Search latency p95 | < 100 ms | 24.36 ms | met |
| Peak RSS of any child process | < 600 MiB | 193.3 MiB | met |
| FTS index size / raw text | <= 3x | 0.43x | met |

* **Import >= 10,000 messages/s.** A heavy personal export has tens of thousands of messages; at this budgeted rate 50,000 messages would import in about five seconds, so `gcr import` stays an interactive command, and a very large export (500,000 messages) in under a minute. At the rate measured in this run (7,524 messages/s) the same sizes take about 7 s and 66 s. Below the budgeted rate the import becomes the slowest step of a workflow and people stop re-importing to keep the database current.
* **Search p95 < 100 ms.** About 100 ms is the commonly used limit under which an interactive answer feels immediate. The CLI and the MCP server answer a model or a person one query at a time, so the tail (p95) matters more than the mean; the budget is on all 200 varied queries, not only the easy ones.
* **Peak RSS < 600 MiB.** GCR runs on a developer laptop, a small CI runner or a Codespace next to an editor and a model client; 600 MiB leaves room on a machine with 2 GiB of free memory. NFR-05 asks for bounded memory: the scaling probe above is the evidence for the shape (memory bounded by the number of conversations and the largest conversation, not by the size of the export), the budget is the absolute ceiling for one process at 50,000 messages.
* **FTS index <= 3x the raw text.** `docs/ARCHITECTURE.md` fixes "about 3x the raw text size" for the INDEX so that search does not multiply the size of a large export. The whole database file is larger because it also keeps the original message JSON (`raw_source_json`) and the block list next to the normalized text (provenance is never discarded); that whole-file ratio is reported in the results table so nobody has to guess what the file costs.

The four targets are engineering judgment, not measured user requirements; changing one needs an ADR, not a quiet edit of this script.

A budget that is "NOT met" is a WARN line on stderr and a row in this table, not a failing build: it is a prompt to look at the change that caused it, or to revisit the budget in an ADR.

## Notes on this run

* The 1-minute load average (0.74 at the start, 1.18 at the end) stayed below the number of CPUs (4), but the script cannot see everything else that ran on the machine.
* The graph build took 40 s for 50,000 messages (441,770 edges). The import of the same data took 6.6 s. The graph build has no NFR-05 budget because it runs on request (`gcr graph build`); `audit` (856.68 ms) and the slowest `stats` group-by (day, 711.89 ms) scan every message.
* The synthetic export has no attachments, no tool messages, no hidden messages and no oversized single message. The numbers say nothing about those paths.

npm run perf                                    # the table and the JSON summary

node scripts/perf-baseline.mjs --messages 2000  # a quick run (seconds)
npm run perf -- --write-doc --date 2026-01-31   # rewrite this page (pass the date: the script never reads the clock)
