# Acceptance record

This is the record of what was actually run to accept GCR `0.2.0-dev.0`, with real results, and of what was **not** run. It is the single place for test counts, durations and dates: other documents point here instead of repeating numbers. It records evidence; it does not claim that GCR works on a real ChatGPT export, because **no real export was ever used**. Everything was run on synthetic data (`fixtures/`, data generated by the tests and by `scripts/perf-baseline.mjs`).

* Tested commits: the gate runs of section 2 started from `8b50b3e` (work tree and fresh clone) and `751bd0f` (Node 22.16.0 and non-root); `751bd0f` differs from `8b50b3e` only by a comment block in `scripts/release-checksums.mjs`. The head **`c2a7738`** (46 commits on `claude/chatgpt-conversation-reader-rraexo`; its changes since `751bd0f` are documentation only: this record, the execution plan, the PR notes, the CHANGELOG) was then run in full once more in a fresh clone from GitHub, see the "Final head" row of section 2. The commit that adds that row changes only this file.
* Date: 2026-10-12 (UTC). The reviews of section 4 ran on 2026-10-11 and 2026-10-12.
* Machine: Linux 6.18 x86_64 sandbox (Firecracker VM), 4 CPUs, 16 GiB RAM, **running as `root`** except where section 2 says otherwise, no GitHub runner, outbound HTTPS only through the sandbox proxy (npm registry reachable, `*.openai.com` not).
* Node: v22.22.0 (SQLite 3.50.4) and v22.16.0, the declared minimum (SQLite 3.49.1; the official binary). TypeScript 7.0.2, npm 10.9.4.
* GitHub Actions was never run: `.github/workflows/gcr-ci.yml` has **never run on GitHub**. Its steps were run here, one by one, as the `gates.sh` sequence below.

## 1. Verdict in one paragraph

All automated gates pass on the tested commit on Node 22.22.0 and 22.16.0, in the work tree, in a fresh clone of the pushed branch and as a non-root user: typecheck, build, the whole compiled suite (7,426 tests, 0 failed), the smoke script, the privacy scans of the tree and of the whole history, `npm audit`, the license inventory, and the freshness checks of the generated documents. The performance baseline **misses its own import-throughput budget** (about 7,500 messages/s against 10,000). Four independent reviews found real defects, including three high-severity ones and one that would have turned the first CI run red; all were fixed or documented and re-checked (section 4). What remains unproven is listed in section 6: above all, behaviour on a real export, on Node 24, Windows and macOS, and in GitHub Actions.

## 3. Performance and coverage

From `docs/PERFORMANCE.md` (one run, 2026-10-12, Node 22.22.0, idle machine: load average 0.7 at the start and 1.2 at the end; 50,000 generated messages in 500 conversations in 5 shards; the page lists the method and its limits):

| Measure | Result | Budget (the project's own, an engineering judgment) | Verdict |
|---|---|---|---|
| Import throughput (`gcr import`, child process) | 7,524 messages/s (6,645 ms) | >= 10,000 messages/s | **NOT met** |
| Search latency p95 (200 queries) | 24.36 ms | < 100 ms | met |
| Peak RSS of any child process | 193.3 MiB (graph build; import 142.2 MiB) | < 600 MiB | met |
| FTS index size / raw text | 0.43x (whole database file: 6.07x) | <= 3x | met |

Memory against export size (peak RSS of `gcr import`, measured as `VmHWM` of the child): 10,000 messages 122.3 MiB, 50,000 messages 142.2 MiB, 250,000 messages 140.3 MiB; five times the data cost 0.99x the memory. An earlier version of this probe measured the child with `process.resourceUsage().maxRSS` and reported 546 MiB for the 250,000-message import: on Linux that value includes the parent's resident size at the moment of `fork`, and the probe's parent held the whole generated export in memory. The same import started from a small parent peaks at about 139 MiB. The regression test for the original defect (import-time retention of the text of every conversation) is `test/ingest/import-runner.heapcap.test.ts` (an 84 MB export imported under a 96 MB heap cap).

A budget that is missed is a `WARN` line, not a failing build. The import-throughput budget was missed in every run of this project (6,860 to 7,657 messages/s on this machine). Nothing here was measured on a real export or a dedicated benchmark machine.

## 4. Independent reviews

Four read-only reviewers attacked or audited the built product in two rounds, each as a separate agent that had to reproduce what it reported. Round 1 ran on 2026-10-11 against commit `caf76d1`; round 2 on 2026-10-12 against `c8062e4` and later. Their findings were then fixed by builders and re-attacked by separate breakers (a fresh agent for each fix batch). Counts below come from the reports, not from a database.

| Lens | Round | What it did | Findings (by its own severity) | Outcome |
|---|---|---|---|---|
| Spec conformance | 1 | ran all 16 command forms of SPEC section 6, the MCP server through the real SDK client, the suite and the smoke script; judged every FR and NFR against `docs/PARITY_MATRIX.md` | 1 high, 3 medium, 6 low, 2 info | high: import memory grew with export size (NFR-05) - fixed with a heap-cap regression test; medium: CLI `get`/`thread` omitted `SOURCE_NOT_FULL_HISTORY`, the SPEC's `graph query "EMBLEM-NLP"` returned an empty graph silently, attachment names were not searchable (FR-15) - all fixed; low and info items fixed or documented; two PARITY verdicts (NFR-05, FR-15) had been overclaims and were corrected |
| Security (black box) | 1 | 38 hostile ZIPs, 9 hostile JSON files, hostile paths, CLI/MCP/SDK arguments, a network/fs/env tracer over 20 CLI processes and a 12-tool MCP session, supply chain, the privacy scanner | 2 high, 2 medium, 5 low, 3 info | high: a dangling symbolic link as `--db` created the target world-readable (ATK-01); the privacy scanner reported "clean" for export-shaped files above 2 MiB under most names (ATK-02) - both fixed; medium: `.gitignore`/no hooks/scanner blind to GCR's own output (ATK-03), raw C1/bidi/TAG characters in MCP results (ATK-04) - fixed; low items fixed; three limits documented, not changed (MCP synchronous reads can take far longer than the 30 s deadline on a 500,000-node conversation, an oversized MCP frame ends the session, hard links inside an approved directory). **No network, credential, cookie, ZIP-escape, SQL/FTS-injection, XSS or approved-root escape was found.** |

| Docs | 2 | executed every command example of the README, user guide, CLI reference, MCP tools, SDK guide, import guide and the SPEC list; cross-document consistency; honesty audit | 6 medium, 6 low, 3 info | fixed: OpenAI wording that the repository claimed not to contain (research notes quoted it; the guides labelled second-hand text OFFICIAL) - removed and relabelled "reported, UNVERIFIED"; missing operator sections (delete your data, SDK use, DB_ERROR recovery); stale performance and test-count statements; non-runnable examples |

Fix batches were each followed by an independent breaker. They found further defects in the first fixes, which are fixed: a one-byte or table-less target file bypassing the symbolic-link check, a FIFO at the database path hanging every read command, the ownership warning missing on the first import, leading blank lines hiding an export from the scanner, a CRLF checkout breaking the installed git hook, a message listing more than 5,000 attachments being cut silently, and, from the test-hardening verifier, a **race in the product** (several processes creating one new database at the same moment failed in 1 to 3 % of runs with "busy" or "not a GCR database"; fixed in `src/db/open.ts` and `src/db/schema.ts`, 0 failures in 80 stress runs afterwards). One breaker finding is **not** fixed and is documented: a failing first import deletes a database file that a concurrently started successful import is already using (2 of 25 tries in the breaker's experiment; `docs/SECURITY_AND_BOUNDARIES.md` section 9).

**The Chromium run.** The exported graph page was executed once in a real headless Chromium 141 by the round-1 security reviewer on 2026-10-11 (Playwright from `/opt/node-tools`, `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`). Subject: an export of four synthetic conversations whose titles, roles, models, tool recipients, urls and text carried script-closing, event-handler, `javascript:` and quote-breaking payloads, made with `gcr graph export --out g.html` (mode 0600), plus hostile `--title` and `--term` values. Actions: all 31 buttons clicked, 24 SVG nodes activated by click and by Enter, an XSS string typed into the search box, and the page loaded with the hashes `#<img onerror>`, `#node="><script>`, `#__proto__`, `#constructor`, `#javascript:`. Observed: the document title stayed `GCR graph export`, 0 dialogs, 0 console or page errors, 0 requests other than file and data URLs, only the two expected `<script>` elements, the payloads present only as text nodes and `<title>` text, and a Content-Security-Policy meta tag with `default-src 'none'`, script hashes and `require-trusted-types-for 'script'`. This is the only real-browser evidence. It is not part of the test suite, it is not repeated in CI and its script was not committed; a screen reader, other browsers and keyboard behaviour beyond click and Enter were not tested.

* **not implemented (gated)**: FR-17: no browser code exists; `npm run test:browser` reports `NOT_RUN`.

## 6. NOT run, not verified, known deviations

NOT run or not verifiable here:

* **Any real ChatGPT or Claude export.** The importer was built from third-party descriptions of the format and has only ever seen synthetic fixtures. Expect surprises.
* **GitHub Actions.** The workflow was never run; the pinned action SHAs were looked up, not executed. The hosted account name `runner` was emulated, not observed.
* **Node 24 and newer, Windows, macOS**, a screen reader, browsers other than one Chromium run, VS Code / Claude Desktop / Codex as MCP hosts (only the official SDK client was used).
* **OpenAI's Terms of Use, Usage Policies and Help Center pages.** Every OpenAI host was unreachable from the sandbox; the platform-policy review required by `AGENTS.md` was **NOT PERFORMED**. Statements about OpenAI's export feature are second-hand and marked "reported, UNVERIFIED".
* An export larger than the synthetic 250,000-message probe (a real multi-gigabyte ZIP64), a genuine 512 MiB `OUTPUT_TOO_LARGE` render (only simulated by forcing the error), the MCP 5 to 50 MiB frame limits and 500,000-node read times (quoted from the security review), real unprivileged runs of the two permission tests, `READ_ONLY_LOCATION` and permission-denied paths as an unprivileged user outside the tests that stub the user id, the concurrent-first-import race beyond the reviewers' experiments, the git hook installer in this repository (only throwaway repositories), encryption at rest (none exists).

Deviations from the supplied documents (all recorded as ADRs in [DECISIONS.md](DECISIONS.md)):

* No v0.1.1 baseline existed (the remote was empty; ADR-0001), so GCR is a clean-room implementation of `SPEC.md`, not an upgrade, and the legacy `chatgpt_*` MCP names are unknown (ADR-0002).
* Node >= 22.16.0, not the runbook's 22.13: Node 22.13 to 22.15 ship `node:sqlite` without FTS5 (ADR-0012).
* CCR has no `LICENSE`; nothing was copied, only features and data shapes were inventoried (ADR-0008).
* `AGENTS.md`, `SPEC.md`, `CODEX_TASK.md` and `docs/REPO_RUNBOOK.md` are the user's supplied files and are byte-identical to the bootstrap commit.
* No pull request was opened (ADR-0006).
