# Changelog

All notable changes to GCR (EMBLEM-NLP ChatGPT Conversation Reader & Writer) are recorded here, in the spirit of
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versions follow the `package.json` version. This file states, for every entry,
what was **tested** (by whom, how, with which numbers) and what was **not**. A passing test run on synthetic data is not evidence that
a real ChatGPT export imports correctly.

## 0.2.0-dev.0 - unreleased

First entry of a clean-room implementation of `SPEC.md` (target "GCR v0.2.0"). It is **not** a release: the package is `private`, there is no
`LICENSE` file (ADR-0008) and no tag. The version `0.2.0-dev.0` was chosen so that it does not imply lineage with the baseline v0.1.1,
which was never available (ADR-0001).

### Added (what exists)

* **CLI `gcr`** (`dist/cli/main.js`): `doctor`, `import`, `import-copy`, `batches`, `list`, `get`, `search`, `branches`, `thread`, `stats`, `audit`,
  `graph build|query|path|neighbors|god-nodes|explain|export`, `draft create|list|show|archive`, `annotate create|update|list|show`, `mcp`, `help`.
  Output formats `markdown` (default), `compact`, `json`, `jsonl`; stable exit codes per error code; stdout carries only the result. 31 help pages are captured in `docs/CLI_HELP.txt`.
* **Local MCP server** (stdio, `dist/mcp/entry.js` or `gcr mcp`): 12 tools (`gcr_list`, `gcr_get`, `gcr_search`, `gcr_branches`, `gcr_thread`, `gcr_stats`, `gcr_audit`, `gcr_graph_query`,
  `gcr_doctor`, `gcr_create_local_draft`, `gcr_update_local_annotation`, `gcr_import_export`). Read-only by default; writes need `--allow-local-writes`; import needs approved roots.
  One result envelope with `source`, `completeness`, `warnings`, `ids`, `untrustedContent`. The legacy `chatgpt_*` alias table is empty because the v0.1.1 names are unknown (ADR-0002).
* **TypeScript SDK** (`Gcr` facade, `src/index.ts`) shared by the CLI and the MCP server; typed results and `GcrError` with 28 stable error codes (`src/errors.ts`).
* **Import** from an official export ZIP, an extracted folder, `conversations*.json`, sharded `conversations-NNN.json` (with or without `export_manifest.json`), a ZIP nested one level, and standard input.
  First-party ZIP reader (STORE/DEFLATE; designed to refuse path traversal, symlinks, encryption and duplicate names, with size, entry-count and compression-ratio limits against decompression bombs; a `../` entry was refused by hand, the rest is covered by the test suite) and streaming JSON splitter with explicit limits. Atomic, idempotent import; immutable snapshots with a
  per-conversation head; account labels; `--strict`. Adapters: ChatGPT (exercised with synthetic data only), Claude export (offline data shape, synthetic only), OpenAI developer API (interface plus a disabled implementation, Mode D).
* **Mode B manual copy** (`import-copy`), always `partial_user_supplied`.
* **SQLite schema v1** (`node:sqlite`, STRICT tables, FTS5 index, immutability triggers, `local_*` tables for drafts, annotations and an append-only audit log, derived graph tables) with versioned migrations.
* **Search**: plain mode (Unicode NFKC, case and accent insensitive, CJK by character, prefix `word*`, implicit AND), `--raw` FTS5 mode, scopes, filters, `--limit/--offset/--cursor` paging, snippets.
* **Branches**: cycle-safe tree analysis, branch ids = leaf ids, active branch only from a valid `current_node` (ADR-0009), opt-in labelled heuristics (`last_child`, `latest_leaf`).
* **Stats and audit** (by role, model, channel, day, conversation, provider, content type; nine audit checks) that never infer a model or a timestamp.
* **Entity extraction and knowledge graph** (URLs, UUIDs, timestamps, tool names, code languages, file names, keywords), deterministic label-propagation communities, query, shortest path, neighbours, god nodes,
  evidence for every edge, and a self-contained offline HTML export (strict Content-Security-Policy, no network references).
* **Local drafts and annotations** (Mode C) with namespaces, an append-only audit log and, for annotations, optimistic concurrency (`--expected-version`); a draft has no "sent" state and carries a manual continuation link.
* **Dev tooling**: privacy scanner (`scripts/privacy-scan.mjs`), dependency license inventory (`scripts/licenses.mjs`), CLI-help capture and MCP-schema dump with `--check` modes, a gated `test:browser` that reports `NOT_RUN`, a smoke script (`scripts/ci-smoke.mjs`), a performance baseline (`scripts/perf-baseline.mjs`), a coverage summary (`scripts/coverage-summary.mjs`), an audit-report generator (`scripts/audit-report.mjs`), release checksums (`scripts/release-checksums.mjs`), opt-in git hooks (`scripts/install-git-hooks.mjs`), a SHA-pinned read-only GitHub Actions workflow and a devcontainer definition.
* **Documentation**: README, user guide, CLI reference, MCP tools, SDK, import guide and format notes, adapters, architecture, decision records ADR-0001 to ADR-0027 (ADR-0013 to ADR-0027 were written after the code existed and are not confirmed by an operator), the committed research notes (`docs/research/`), the audit report (`docs/AUDIT_REPORT.md`), the acceptance record (`docs/ACCEPTANCE.md`), browser gate, execution plan, PR notes.
* **Mode E (browser interaction) ships no code** (ADR-0010, `docs/BROWSER_GATE.md`).

### Fixed and hardened after the first independent review (2026-10-12)

A final multi-lens review (spec conformance, black-box security, test quality, docs) found the defects below; each was reproduced first, fixed with a regression test that fails without the fix, and attacked again by a second reviewer.

* **Import memory (NFR-05, was HIGH).** Pass 1 of the importer kept conversation-id strings that pinned the full text of every conversation, so a 210 MB export died under a 192 MiB heap cap. Keys are now flattened copies; `test/ingest/import-runner.heapcap.test.ts` imports an 84 MB export under a 96 MB heap cap. Memory is O(number of conversations) plus the largest conversation, not flat (ADR-0026). The perf script now probes 1/5x, 1x and 5x the data and warns above 1.6x peak RSS.
* **Database paths (ATK-01, was HIGH).** A dangling symbolic link as `--db` created the target world-readable. The path is now inspected with `lstat` first: symbolic links to nothing/empty/uninitialised files, FIFOs, devices and stray `-wal`/`-shm`/`-journal` files are refused (`SYMLINK_DB_PATH`, `STRAY_SIDECAR_FILES`, `not_a_regular_file`); a failed first import removes only files it created (ADR-0022, ADR-0027). A warning on stderr appears when the default `./.gcr` database is not owned by the current user.
* **Privacy scanner fails closed (ATK-02, was HIGH; ATK-03, ATK-09).** Files over the size cap were skipped silently, so a real export (usually larger than 2 MiB) under any name except `conversations*.json` passed. Large files are now judged through head and tail windows and reported as `unscanned-large-file`; GCR's own output (graph pages, CLI/MCP JSON and renderings) is recognised as `gcr-output-file`; more credential shapes; `--staged` mode and opt-in git hooks (`node scripts/install-git-hooks.mjs`); a wider `.gitignore` (ADR-0025).
* **MCP output (ATK-04).** Tool results show DEL, C1, bidi, TAG and line-separator characters as visible `\uXXXX` escapes (text block and `structuredContent`), and the size cap is measured on the escaped form (ADR-0023). Regular files with more than one hard link are refused as import paths under approved roots (ATK-10).
* **Errors (ATK-06, ATK-08).** Output too large for one string is `INVALID_ARGUMENT` / `OUTPUT_TOO_LARGE`, not `INTERNAL_ERROR`; a foreign SQLite file read says "not a GCR database"; an element too large to sniff says to pass `--provider`.
* **Spec divergences.** `gcr get` / `gcr thread` now print the same warnings as the SDK and MCP in every format, with `SOURCE_NOT_FULL_HISTORY` first (SPEC-02); `gcr graph query "EMBLEM-NLP"` splits hyphenated terms (`TERM_SPLIT`) and reports `NO_MATCHING_NODE` instead of a silent empty graph (SPEC-03); new search scope `attachments` matches attachment file names and MIME types, metadata only, no index, no schema change (SPEC-04, ADR-0024; `--scope all` now includes attachment names); `NO_BRANCHES` distinguishes an empty tree from messages no root reaches (SPEC-06); `branchProvenance` is `null` when no tree check ran (SPEC-07, breaking for typed consumers); a symbol-only query says so (SPEC-08).
* **New tooling.** `scripts/audit-report.mjs` generates [docs/AUDIT_REPORT.md](docs/AUDIT_REPORT.md) (branch/model provenance audit of the synthetic fixtures); `scripts/release-checksums.mjs` writes and verifies a `SHA256SUMS` manifest of the `npm pack` tarball (NFR-02 is "partial": no published release, no signature, workflow never run); the Phase 0 research notes are committed under [docs/research/](docs/research/README.md).
* **Round 2 (test quality and docs), 2026-10-12.** `npm test` failed for the account names that CI images use (`runner`, `node`, `nobody`, ...) because the performance-doc test searched the page for the bare user name: the leak check is now shape-based (TQ-01; verified with `os.userInfo()` emulated as those names). `privacy-scan --history` said "clean" in a shallow clone (what `actions/checkout` produces by default): it now reports `scan-truncated` (TQ-02). A **product race** found by the verifier: several processes creating one new database at the same moment failed in 1 to 3 % of runs with "busy" (`PRAGMA journal_mode = WAL` ignores `busy_timeout`) or "not a GCR database"; both are fixed (`src/db/open.ts`, `src/db/schema.ts`). Environment-robust tests (paths with spaces or non-ASCII, long `TMPDIR`, umask 0027/0077, non-root), a pinned exit-code table, more mutation-killing assertions. The docs no longer reproduce or label as OFFICIAL any OpenAI wording (the research notes and guides had quoted a search summary), a "Delete your data" section, SDK use outside the repository, DB_ERROR recovery rows, runnable examples. The perf script's child-RSS measurement is corrected (see Lessons).
* **Tests changed by the fix wave.** Three existing tests were updated because the behaviour they pinned changed on purpose (MCP escapes instead of raw separators); no test was weakened or deleted.

### Tested

Everything was run on **synthetic, invented data** only, on Linux x64 in a shared sandbox as `root` (so two permission tests skip), without a GitHub runner. The exact commands, their real output, counts, durations and dates (typecheck, build, full compiled suite on Node 22.22.0 and on the declared minimum 22.16.0, the same in a fresh clone of the pushed branch, smoke on both Node versions, privacy scan of the tree and of the whole history, `npm audit`, license inventory, CLI-help / MCP-schema / audit-report freshness, release-checksum reproducibility, performance and coverage runs) are recorded in **[docs/ACCEPTANCE.md](docs/ACCEPTANCE.md)**. Numbers are deliberately not repeated here: they went stale within the hour while this project was being written (see Lessons).

### NOT tested / not verified

* **A real ChatGPT export.** None was available. File names, the `mapping` tree, shards, the manifest, asset naming, `children` and `current_node` presence, timestamps and model fields are community reports (see `docs/IMPORT_FORMAT.md`) exercised only by invented fixtures. **GCR has never imported a real export.**
* **The GitHub Actions workflow has never run on GitHub.** `.github/workflows/gcr-ci.yml` and `.devcontainer/devcontainer.json` were authored and their steps were run locally, one by one; the pinned action SHAs were resolved with `git ls-remote` on 2026-10-10 and not re-checked; the runner images and the Node versions they install were never exercised.
* **Node 24 and newer.** No such binary was available. Node 22.16.0 to 22.22.0 only (and 22.13.1 for the refusal path); the other Node 22.x binaries listed in ADR-0012 were run at that time, not in this entry.
* **Windows and macOS.** Path handling, file modes and `realpath` behaviour on those systems are untested.
* **OpenAI Terms of Use, Usage Policies and help-center pages: not readable from the sandbox, so the platform policy review was NOT PERFORMED.** No OpenAI clause is quoted or paraphrased as fact in this repository. The statements about how to request an export are "reported, UNVERIFIED" (paraphrases of a search summary; no quotation; not labelled OFFICIAL) and could not be checked against OpenAI's page.
* **Real MCP clients** (VS Code, Claude Desktop, Codex): only the official SDK client was used. The configuration snippets follow those clients' documented shape as the authors knew it. HTTP/SSE transports do not exist.
* **Encryption at rest**: none exists. Disk-level encryption and file-permission behaviour under other users were not tested.
* **Permission-denied paths**: the suite ran as `root`, where file permissions are not enforced (two tests skip).
* **Browsers and assistive technology on the graph HTML**: the page was executed once in a real Chromium 141 by an independent reviewer (inert under hostile titles, ids, hashes and search input; not part of the suite, not repeated in CI); a screen reader, other browsers and keyboard behaviour beyond click/Enter were not tested.
* **Live behaviour of the browser features**: none exist (Mode E is gated; Mode D is a disabled adapter). No "live send" of any kind was attempted or is possible.
* **`npm ci` against the live registry** was run in fresh clones of the pushed branch by the lead and by two reviewers (see [docs/ACCEPTANCE.md](docs/ACCEPTANCE.md)); it needs the registry once. The package is not published to npm.
* **Large inputs on real hardware**: the 50,000-message synthetic scale tests (`test/ingest/*.scale.test.ts`) and the 50,000-message baseline script (`scripts/perf-baseline.mjs`) used generated data; no real-size export (hundreds of MB, multi-GiB ZIP64) was imported. The measured baseline is in `docs/PERFORMANCE.md` (one run in a shared, loaded sandbox; not summarised here).
* **Parity with the Claude Conversation Reader (CCR)** is a feature inventory only; no CCR code was copied or run, and CCR has no `LICENSE` file (ADR-0008).

### Known issues

* CLI messages sometimes use SDK vocabulary: the limit remedy says `maxElementBytes` (flag: `--max-element-bytes`), the annotation-conflict remedy says `getAnnotation` (command: `gcr annotate show`), the ambiguity remedy mentions an "object reference".
* The nested-ZIP limit (256 MiB per inner archive) has no CLI flag and no SDK import option: it is the constant `MAX_NESTED_ZIP_BYTES` in `src/ingest/layout.ts`, and the import runner passes only `provider` and `passes` to the discovery function.
* A conversation object that has both `mapping` and a `conversations` array is skipped as `NOT_A_CONVERSATION`; the wrapper rule applies only to objects without `mapping`.
* The batch-level `completeness` is the adapters' nominal level; each conversation's own value is authoritative (`COMPLETENESS_BELOW_BATCH_LEVEL` reports the difference).
* `gcr stats` and `gcr audit` print `formatProfiles: []`; the observed format profile is available only in the import report.
* `gcr batches` shows message counts without the structural root rows, while the import report's `messages.stored` includes them (43 versus 39 in the demo); both are correct, the difference is not explained in the output.
* Branch ids are compared by UTF-16 code units in the branch analysis but SQLite orders by UTF-8 bytes; the two orders differ only for ids outside the Basic Multilingual Plane. Documented in `docs/ARCHITECTURE.md` section 2 (the mixed case is NOT VERIFIED by a test).
* The ZIP reader does not compare local-header CRC and sizes with the central directory when the data-descriptor bit is clear (design decision, recorded as ADR-0017). A JSON nesting depth of 10,000 aborts a file while the adapter keeps 256 levels (recorded as ADR-0013).
* `FEATURE_GATED` and `REMOTE_ACCESS_FORBIDDEN` are defined error codes that no code path emits.
* The result-size and deadline situations of the MCP server surface as `INTERNAL_ERROR` with a `details.reason`; a dedicated code is proposed in `docs/MCP_TOOLS.md`.
* `node:sqlite` is still experimental in Node 22; GCR hides exactly that one `ExperimentalWarning`. The installed MCP SDK drags HTTP-server packages (for example `express`) into `node_modules`; GCR never imports them (a test checks the import allow-list).
* At milestone head `bc6af53` the suite has one failing test (`test/sdk/errors.test.ts`, a test expectation, fixed in `8cfb1b2`); see `docs/PR_NOTES.md`.
* The suite contains a timing-sensitive scale test (imports 400 conversations without pathological slowness) that, according to the message of commit `8cfb1b2`, failed once under CPU contention from concurrent agents at about 06:05 UTC on 2026-10-11 (not observed by the author of this entry); it passed in all later full runs, including the round-2 reviewer's runs under four busy loops (see [docs/ACCEPTANCE.md](docs/ACCEPTANCE.md)). Whether it can still fail on a much slower machine is **NOT VERIFIED**. A second wall-clock test, `test/entities/extract.redos.test.ts` ("growth is linear, not quadratic"), failed once in a full run under that load ("4x input took 261 ms vs 13 ms") and passed five of five times in isolation, so timing assertions in the suite can fail on a loaded machine without a defect.
* **The smoke script (`scripts/ci-smoke.mjs`, the CI step `npm run smoke`) failed twice in 10 runs on 2026-10-11** while the machine was heavily loaded (load average 11 to 13) and a rebuild may have been in progress; the cause was **never diagnosed**. It did not recur on 2026-10-12: 10 of 10 runs on an idle machine and 6 of 6 under eight busy loops (load average 6.5 to 10.4); see [docs/ACCEPTANCE.md](docs/ACCEPTANCE.md). Until the 2026-10-11 failure is understood, a green run is weaker evidence than the "SMOKE OK" line suggests.

### Lessons

* **A peak-memory number measured in a child process can be the parent's.** On Linux `process.resourceUsage().maxRSS` of a spawned child includes the parent's resident size at fork time, so a 5x scaling probe run from a parent that held the whole generated export reported 546 MiB where the same import started from a small parent peaks at 139 MiB. The probe was nearly published as a finding against the memory bound; it now reads `VmHWM` of the child. Cross-check any measurement that surprises you with a second method.
* **A leak check that looks for the OS user name must not search for the bare name.** CI images name the account `runner` or `node`, words the prose of the checked document may contain. The check looks for path- and `user@host`-shaped occurrences.
* **Two checkouts of one commit have the same tarball hash only if their file modes agree**; `npm pack` records the permission bits on disk, git tracks only the executable bit. Build release artifacts from a fresh clone.

* **The baseline was missing (ADR-0001).** The task said to use the "existing TypeScript v0.1.1" as baseline and the runbook said to import its folder. The remote repository was empty and only four documents were supplied. GCR was therefore built from the specification, Phase 0 "reproduce the baseline" is recorded as **not possible**, no `chatgpt_*` tool names could be preserved (ADR-0002), and no parity or lineage with v0.1.1 is claimed.
* **The Node minimum was wrong in the runbook (ADR-0012).** The supplied runbook says Node 22.13 with "built-in Node SQLite". Real binaries showed that `node:sqlite` has no FTS5 before 22.16.0 (SQLite 3.47.2 in 22.13/22.14, 3.49.1 in 22.15, FTS5 present from 22.16.0): on 22.13 the first schema migration failed and hundreds of tests failed with "no such module: fts5". GCR now requires `>=22.16.0`, probes FTS5 before touching a file and fails with a clear `DB_ERROR` (`FTS5_UNAVAILABLE`).
* **Do not trust a green number without its date and runtime.** Suite totals changed from 5,771 (ADR-0012, earlier) to 5,807 (milestone head bc6af53) to 6,568 and then 6,750 as tests were added; the figures above are tied to a command, a Node version and a date.
* **Never message a running workflow agent** that edits the same files: it resumed as a second concurrent writer once and overwrote work (process lesson, recorded in the lead notes).
* **Measure on a clean commit, not on a moving tree.** While other agents were editing the sources, runs on the working tree gave transient failures that said nothing about the code at any commit: four tests failed on Node 22.16.0 because the rebuilt `dist/` and `docs/mcp-tool-schemas.json` disagreed for a few minutes about one annotation hint, and a wall-clock ratio test (`test/entities/extract.redos.test.ts`, "growth is linear, not quadratic") failed once under CPU load (load average about 10 to 13) and passed five of five times when re-run alone. The final numbers above were taken on a clean `HEAD`.
* **Quoted numbers go stale within the hour.** While this entry was being fact-checked, the smoke script grew from 41 to 51 checks, `HEAD` moved from `91caaf2` to `1e27fa0` and then to `d8e111a`, the file count of the privacy scan went from 338 to 340 and a new test file appeared. Every figure above names the command, the commit or tree it was measured on and the time; re-measure before quoting one.
* **Synthetic evidence has a ceiling.** The fixtures encode what community reports say; they cannot reveal what a current export really contains. The first real export is expected to teach something.
